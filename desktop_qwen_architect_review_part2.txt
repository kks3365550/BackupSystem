수석 소프트웨어 아키텍트로서, 요청하신 **3번 항목(안전하면서도 단계 전환 딜레이를 0.1초 수준으로 매끄럽게 만드는 엔지니어링 최적화 방안)** 에 대해 구체적인 기술적 솔루션을 제시합니다.

0.1초(100ms)라는 시간은 인간이 '연속성'을 인식하는 임계값에 가깝습니다 이를 달성하되, 시스템 안정성(안전성)을 해치지 않기 위해 **동적 스케줄링, 메모리 관리, 그리고 네트워크/디스플레이 파이프라인 최적화**의 3가지 핵심 축을 중심으로 설계합니다.

### 1. 전이 애니메이션의 '비동기 프리로딩' 및 GPU 가속 렌더링 (Asynchronous Pre-loading & GPU-Accelerated Rendering)

전환 딜레이의 대부분은 **다음 상태의 리소스 로드**와 **UI 재구성(Re-layout)** 에 소요되는 시간입니다. 이를 0.1초 이하로 줄이기 위해 CPU의 메인 스레드를 가볍게 유지하고, 무거운 작업을 GPU와 별도 스레드로 위임하는 전략을 사용합니다.

*   **구체적 구현 방안:**
    *   **GPU-Only Transition:** UI 전환 시 CPU에서 DOM 조작이나 복잡한 로직을 수행하지 않고, CSS `transform` 및 `opacity`를 사용하여 GPU 하드웨어 가속을 강제합니다. 이는 CPU의 메인 스레드 블록을 방지하여 프레임 드롭을 최소화합니다.
    *   **Offscreen Rendering (오프스크린 렌더링):** 현재 화면에서 벗어난 다음 단계의 컴포넌트를 `will-change: transform, opacity` 속성으로 사전에 GPU 메모리에 로드해 두는 것입니다.
    *   **Web Workers 활용:** 데이터 파싱이나 상태 계산 같은 CPU 집약적 작업은 메인 스레드가 아닌 Web Worker에서 수행하고, 완료된 상태만 `postMessage`를 통해 UI 스레드에 전달합니다.
*   **안전성 보장:**
    *   GPU 메모리 오버플로우를 방지하기 위해 `requestAnimationFrame` 내에서 렌더링 버퍼를 관리하고, 이전 프레임이 완전히 폐기된 후 다음 프레임을 로드하는 **Double Buffering** 패턴을 적용합니다.
    *   Worker 스레드의 예외 발생 시 메인 스레드와의 통신 채널을 끊지 않고, 기본 상태(Fallback State)로 즉시 롤백하는 에러 핸들링을 구현합니다.

### 2. 상태 관리의 '가상화' 및 메모리 풀링 (State Virtualization & Object Pooling)

전환 과정에서 객체의 생성과 파괴가 반복되면 Garbage Collection(GC) 스택이 발생하여 **Jank(지체)** 를 유발합니다. 이를 방지하기 위해 객체를 재사용하고, 불필요한 상태 변경을 제거합니다.

*   **구체적 구현 방안:**
    *   **Object Pooling:** 전환 시마다 생성되는 DOM 노드나 객체를 미리 생성해 두는 풀(Pool)에서 가져와 사용하고, 종료 시 삭제하지 않고 풀에 반환하는 방식을 사용합니다.
    *   **Immutable State Diffing:** 상태 변경 시 전체 객체를 재생성하지 않고, 변경된 프로퍼티만 비교(Diffing)하여 최소한의 DOM 조작만 수행하도록 설계합니다.
    *   **Pre-computed Layout:** 다음 단계의 레이아웃 정보를 현재 단계가 종료되기 전에 미리 계산해 두어, 전환 시작 시 즉시 적용할 수 있도록 합니다.
*   **안전성 보장:**
    *   풀링된 객체의 상태가 이전 사용자와 혼동되지 않도록, 매번 재사용 시 **State Reset Protocol**을 강제 적용합니다.
    *   메모리 리크를 방지하기 위해 `WeakRef`와 `FinalizationRegistry`를 활용하여, 참조가 사라진 객체는 자동으로 풀에서 제거되도록 설계합니다.

### 3. 네트워크/데이터 전송의 '스펙ulative Prefetching' 및 로컬 캐시 우선순위 (Speculative Prefetching & Local Cache Priority)

만약 단계 전환이 서버 데이터에 의존한다면, 네트워크 지연은 0.1초를 깨뜨리는 최대 요인입니다. 이를 해결하기 위해 서버 요청을 '반드시 필요한 순간'이 아니라 '예측 가능한 순간'에 미리 수행합니다.

*   **구체적 구현 방안:**
    *   **Predictive Fetching:** 사용자의 행동 패턴(클릭, 스크롤)을 분석하여 다음 단계에서 필요할 데이터를 현재 단계가 종료되기 전에 미리 요청합니다.
    *   **Edge Caching:** CDN 또는 엣지 노드에서 데이터를 캐시하여, 원본 서버까지의 RTT(Round Trip Time)을 제거합니다.
    *   **Optimistic UI:** 서버 응답을 기다리지 않고, 로컬 상태 기반으로 UI를 즉시 전환하고, 서버 응답이 도착하면 조용히(Silently) 동기화하는 방식입니다.
*   **안전성 보장:**
    *   **Consistency Check:** 서버 응답이 로컬 예측과 일치하지 않을 경우, 즉시 로컬 상태를 롤백하고 서버 데이터를 우선 적용하는 **Conflict Resolution** 로직을 구현합니다.
    *   **Timeout & Fallback:** prefetch 요청이 50ms 이상 지연되면, prefetch 데이터를 무시하고 로컬 캐시나 기본 템플릿으로 전환하여 사용자 체감 지연을 0.1초 이내로 유지하는 안전장치(Timeout Guard)를 설정합니다.
