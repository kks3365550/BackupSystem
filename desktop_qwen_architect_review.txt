# 대규모 분산/로컬 백업 시스템: 단계 전환(Transition) 병목 현상 분석 및 아키텍처 최적화

## 1. 각 단계 Transition의 기술적 근본 원인(Root Causes)

현재 관측되는 "체감상 멈칫거리며 뚝뚝 끊기는 현상"은 **I/O 바인드(Bound) 상태의 비동기 전환 실패**와 **메모리/파일 시스템 리소스 경쟁**이 결합된 결과입니다. 각 단계의 Transition 병목을 기술적으로 분해하면 다음과 같습니다.

### 1.1 스냅샷 로드(Step 1) → 디렉토리 병렬 스캔(Step 2)
- **JSON 매니페스트 파싱 병목**: 61MB→93MB로 증가한 JSON 매니페스트는 단일 스레드에서 순차 파싱 시 **CPU 단일 코어 100% 점유**를 유발합니다.
- **GC(Garbage Collection) 트리거**: 매니페스트 객체(26.3만 파일의 metadata)가 메모리에 동시에 로드되므로, **Young Generation GC** 또는 **Major GC**가 발생하여 **Stop-The-World(STW)** 지연이 발생합니다.
- **디스크 I/O 컨테스트**: JSON 로드 완료 직후 디렉토리 스캔이 시작되면, **OS 페이지 캐시(Page Cache)** 가 JSON 데이터와 디렉토리 엔트리를 위해 경쟁하며, **I/O Wait** 상태가 급증합니다.

### 1.2 디렉토리 병렬 스캔(Step 2) → Fast-Path mtime/size 차분 비교(Step 3)
- **스캔 결과 버퍼링**: 병렬 스캔이 완료된 후, 결과(26.3만 파일의 stat 정보)를 **단일 메모리 구조에 병렬 수집**하는 과정에서 **Lock Contention**이 발생합니다.
- **inode 캐시 압축**: 디렉토리 스캔 시 `stat()` 시스템 호출이 대량으로 발생하여 **inode cache**가 채워지고, 차분 비교 단계에서 다시 `stat()`를 호출하면 **cache miss**가 발생하여 디스크 I/O가 재발생합니다.
- **스레드 풀 전환**: 스캔 스레드 풀을 차분 비교 스레드 풀로 전환하는 과정에서 **스레드 컨텍스트 스위칭(Context Switch)** 과 **스레드 풀 재구성**이 발생하여 **latency spike**가 발생합니다.

### 1.3 Fast-Path 차분 비교(Step 3) → 슬라이딩 윈도우 패킹(Step 4)
- **차분 결과 정렬/필터링**: 변경된 파일 목록을 **패킹 순서(디렉토리 트리 순서 또는 크기 순서)** 에 정렬하는 과정에서 **O(N log N) 정렬**이 발생하여 CPU를 점유합니다.
- **Pack File 헤더 작성**: 슬라이딩 윈도우 패킹 시작 전, **Pack File 헤더(메타데이터, 체크섬, 압축 알고리즘 정보)** 를 디스크에 기록하는 **fsync/fsync** 호출이 발생하여 **I/O 바인드** 상태에 빠집니다.
- **압축 컨테이너 초기화**: zlib/lz4 등 압축 라이브러리의 **context allocation**이 발생하여 **메모리 할당**과 **CPU 캐시 미스**가 동시에 발생합니다.

### 1.4 슬라이딩 윈도우 패킹(Step 4) → 무결성 샘플 복원 검증/WAL 체크포인트(Step 5)
- **Pack File flush**: 패킹 완료 후 **Pack File을 디스크에 flush**하고 **fsync**를 호출하여 **데이터 영구화**를 보장합니다. 이 과정에서 **I/O 바인드** 상태가 발생하고, **I/O Wait**가 급증합니다.
- **샘플 복원 검증**: 99% 무결성 샘플 복원 검증은 **Pack File을 다시 읽기**하여 **디스크 I/O**를 발생시키고, **압축 해제(decompression)** 과정에서 **CPU 단일 코어 100% 점유**를 유발합니다.
- **WAL 체크포인트 기록**: WAL(Write-Ahead Log) 체크포인트를 기록하는 과정에서 **WAL 파일의 fsync**가 발생하여 **I/O 바인드** 상태가 지속됩니다.
- **GC 트리거**: 검증 과정에서 생성된 **임시 객체(解压된 데이터 버퍼, 체크섬 계산 결과)** 가 메모리에 쌓여 **Major GC**가 발생하여 **STW 지연**이 발생합니다.

### 1.5 공통 근본 원인
| 원인 | 영향 |
|------|------|
| **Stop-The-World GC** | 매니페스트 로드, 검증 단계에서 STW 지연 발생 |
| **I/O Contention** | JSON 로드, 디렉토리 스캔, Pack flush, 샘플 검증에서 I/O Wait 급증 |
| **Lock Contention** | 스캔 결과 수집, 차분 비교 결과 정렬에서 Lock 경쟁 |
| **Context Switch** | 스레드 풀 전환, 스레드 재구성에서 latency spike |
| **Cache Invalidation** | inode cache, page cache, CPU cache의 invalidation으로 인한 I/O 재발생 |

## 2. 아키텍처 변경 시 반드시 주의해야 할 잠재적 리스크

### 2.1 데이터 무결성 파손 리스크
- **Pack File 중도 손상**: 슬라이딩 윈도우 패킹 중 **전원 차단** 또는 **디스크 오류**가 발생하면, **Pack File이 불완전** 상태로 남고, **체크섬 검증 실패**로 인해 **전체 백업 실패**가 발생합니다.
- **WAL 체크포인트 불일치**: WAL 체크포인트 기록 중 **fsync 실패** 또는 **전원 차단**이 발생하면, **WAL와 실제 데이터 불일치**가 발생하여 **롤백 시 데이터 손실**이 발생합니다.
- **샘플 검증 누락**: 무결성 샘플 복원 검증에서 **샘플 선택 알고리즘의 불균형**이 발생하면, **실제 손상된 파일이 샘플에 포함되지 않아** 무결성 검증이 **False Positive**를 유발합니다.

### 2.2 OOM(Out of Memory) 리스크
- **매니페스트 메모리 초과**: 26.3만 파일의 metadata를 **동시에 메모리에 로드**하면, **Java Heap** 또는 **C++ Heap**이 초과되어 **OOM Killer**에 의해 프로세스가 강제 종료됩니다.
- **Pack Buffer 초과**: 슬라이딩 윈도우 패킹 시 **압축 버퍼**와 **입력 버퍼**가 동시에 메모리에 쌓여 **메모리 초과**가 발생합니다.
- **검증 버퍼 초과**: 무결성 샘플 복원 검증 시 **解压된 데이터 버퍼**가 메모리에 쌓여 **메모리 초과**가 발생합니다
