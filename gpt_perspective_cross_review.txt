# 대규모 분산 백업 시스템 아키텍처 분석: FastCDC + Pack + SQLite WAL + zstd + Ed25519

## 1. 단계 전환 시 프리징을 유발하는 결정적 병목 3가지

### ① SQLite WAL 체크포인트의 I/O 블로킹 (가장 결정적)

**원인:**
- SQLite WAL 모드에서 `PRAGMA wal_checkpoint(TRUNCATE)` 또는 `PASSIVE` 호출 시, WAL 파일의 모든 변경 사항을 메인 DB 파일로 **동기화적으로 flush**해야 합니다.
- 17만 → 26.3만 건으로 파일 수가 증가하면, WAL 파일 크기가 비선형적으로 증가하며, 체크포인트 시점의 **메모리 매핑 페이지 수**가 급증합니다.
- `zstd` 압축 컨테이너의 metadata(인덱스)가 SQLite에 저장되어 있다면, 체크포인트 시점의 **페이지 수 = 컨테이너 인덱스 엔트리 수**에 비례하여 I/O 양이 급증합니다.
- OS 페이지 캐시의 dirty page flush가 **CPU 단일 스레드**에서 serial로 처리되며, 26.3만 건 규모에서는 체크포인트 완료까지 **수백 ms ~ 수 초**까지 지연됩니다.

**특징:**
- `fdatasync()` 또는 `fsync()` 호출 시 OS 스케줄러가 I/O wait 상태로 전환
- 다른 스레드/프로세스의 I/O와 경쟁하여 **latency jitter** 발생
- WAL 파일이 SSD/NVMe에 있어도, **filesystem journal** 또는 **write-back cache** flush 시점의 불확실성

### ② FastCDC의 CDC(Content-Defined Chunks) 스캔의 CPU/메모리 병목

**원인:**
- FastCDC는 rolling hash 기반의 CDC를 사용하며, 26.3만 건 파일의 **전체 스캔** 시:
  - **메모리 버퍼링**: 각 파일의 chunking을 위해 파일 내용을 메모리에 로드 (I/O + CPU)
  - **Rolling hash 계산**: Rabin-Karp 또는类似 알고리즘의 **CPU-bound** 연산
  - **26.3만 건 × 평균 파일 크기**에 비례하여 **메모리 사용량**이 급증
- 이전 스냅샷의 CDC 인덱스(26.3만 건의 chunk hash)를 **인메모리 로딩** 시:
  - **GC/메모리 할당** overhead (Java/Go/C++ 등 언어에 따라 다름)
  - **cache miss** 증가로 CPU pipeline stall
- **단계 전환 시점**에 CDC 스캔이 시작되면, 이전 단계의 **버퍼/인덱스 해제**와 **신규 스캔 버퍼 할정**이 동시에 발생하여 **메모리 압축**이 발생

**특징:**
- CPU utilization 100%로 상승 후, **context switch** 증가
- 메모리 allocation/deallocation의 **fragmentation**으로 인한 latency
- 17만 → 26.3만 건은 **~54% 증가**로, CDC 인덱스 메모리 사용량도 비례하여 증가

### ③ Pack 컨테이너의 zstd 압축 + Ed25519 서명 시점의 CPU 병목

**원인:**
- **zstd 압축**:
  - `zstd`의 **high compression ratio** 모드(예: level 19+)는 CPU-intensive
  - 26.3만 건의 chunk를 **단일 컨테이너**로 압축 시, **compression dictionary**의 학습/사용이 CPU-bound
  - **단일 스레드**로 압축하면, **CPU 1 코어**가 100% 사용
- **Ed25519 서명**:
  - Ed25519 서명은 **CPU-bound** 연산 (elliptic curve operations)
  - 26.3만 건의 chunk hash를 **각각 서명** 시, **수천~수만 번의 EC operation**
  - **단일 스레드**로 처리 시, **수백 ms ~ 수 초** 소요
- **단계 전환 시점**에 압축 + 서명이 **serial로 실행**되면:
  - **CPU 단일 코어**가 100% 사용
  - 다른 단계의 **I/O wait** 또는 **CPU-bound** 작업이 **block**
  - **pipeline stall** 발생

**특징:**
- CPU utilization 100% (단일 코어)
- **I/O와 CPU가 serial로 실행**되어 pipeline 효율 저하
- **서명 검증** 시점에도 동일한 CPU 병목 발생
